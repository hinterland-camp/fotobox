2 · Feature A — hinterland app download on the guest page Missing

Goal: after scanning the QR code, a guest sees their photo, can download it, and gets a prominent, branded call-to-action to install the hinterland app.

A1 · Extend the branding config with an app CTA

The Branding shape (in apps/web/server/api/branding.get.ts and apps/web/app/pages/photo/[id].vue) currently has logo, tagline, links[]. Add:

interface Branding {
  logo: string
  tagline: string
  links: { label: string; url: string }[]
  appCta?: {
    headline: string        // "Get the hinterland app"
    appStoreUrl?: string    // iOS App Store link
    playStoreUrl?: string   // Google Play link
    fallbackUrl?: string    // hinterland.camp landing page
  }
}
  • Move the Branding interface into packages/shared/src/index.ts (it is currently duplicated in the API handler and the page)
  • Parse and validate appCta in branding.get.ts with safe defaults (omit section if unset)
  • Create a real apps/web/branding.json with hinterland logo, tagline, links, and store URLs (and document it in the README)

A2 · Render the CTA on the download page

  • Below the "Download Photo" button in photo/[id].vue: a visually distinct card — hinterland logo, headline, App Store / Play Store badge buttons
  • Optional: user-agent sniff (client-side) to show only the relevant store badge on iOS/Android, both on desktop
  • Mobile-first layout (guests arrive via phone QR scan); keep the photo + download button above the fold, CTA directly beneath
  • Update Open Graph tags to use hinterland branding in the page title

A3 · Acceptance criteria

  • Scanning the QR opens /photo/:id showing the framed photo
  • "Download Photo" saves the full-resolution PNG to the phone
  • App CTA visible without scrolling past the fold on a typical phone viewport (390 × 844)
  • CTA hidden gracefully when appCta is not configured
  • nuxt typecheck and oxlint pass

Effort: ~half a day, no architectural risk.

3 · Feature B — run on the old Windows tablet Missing

Goal: an installable, auto-starting kiosk build of the desktop app for the event tablet. Today there is no packaging config at all — the app only runs via electron-vite dev.

B0 · Decision gate: identify the tablet Blocker

Two facts about the tablet decide everything else — check Settings → System → About on the device:

Tablet runs…Consequence
Windows 10 / 11, 64-bitEasy path: keep Electron 40, build x64 NSIS installer
Windows 10, 32-bit (common on old Atom tablets)Build ia32 target; verify the pinned Electron version still ships ia32 Windows binaries — if not, pin the newest version that does
Windows 8.1 / 8 / 7Must downgrade to Electron 22.3.x (last release supporting Win 7/8/8.1). Requires checking that Vite 7 renderer output (ES2020+) still runs in its Chromium 108 — likely fine, but verify; otherwise lower the renderer build target

B1 · Packaging with electron-builder

  • Add electron-builder to apps/desktop and an electron-builder.yml: appId, productName: Fotobox, win.target: nsis, arch per B0
  • Wire scripts: "build:win": "electron-vite build && electron-builder --win"
  • Add electron-builder to root pnpm.onlyBuiltDependencies if it needs postinstall (known pnpm 10 gotcha in this repo)
  • NSIS options: per-machine install, desktop shortcut, runAfterFinish
  • Build on a Windows machine or VM (cross-building NSIS from macOS works via Wine but is flaky — prefer a Windows build, or a GitHub Actions windows-latest job)

B2 · Kiosk hardening on Windows

  • Auto-launch on boot: app.setLoginItemSettings({ openAtLogin: true }) or a shortcut in the Startup folder (more reliable on old Windows)
  • Verify kiosk shortcuts: current code blocks Cmd+Q/Alt+F4 — confirm Alt+F4, Win key, and Ctrl+Alt+Del edge behavior on the actual device (Ctrl+Alt+Del cannot be blocked; document the exit password flow instead)
  • Touch input: flow is tap-driven already; verify no hover-dependent UI in the new styling pass, and hide the cursor in kiosk mode (cursor: none)
  • Disable Windows Edge-swipe gestures / notifications via tablet's kiosk or assigned-access settings (documented as a setup checklist, not code)
  • Prevent display sleep: powerSaveBlocker.start('prevent-display-sleep') while in photobooth mode

B3 · Performance on weak hardware (old Atom/Celeron tablets)

  • Cap camera capture resolution via getUserMedia constraints (e.g. 1280×720 default, configurable in settings) — full-res canvas compositing on an Atom can exceed the 1 s budget
  • Test compositing time on-device; if slow, composite via createImageBitmap + a single canvas draw (already the approach) and avoid toDataURL for large images — prefer canvas.toBlob
  • Run the 8-hour soak test from the PRD success metrics on the actual tablet (watch for memory growth from the retry interval and data-URL churn)

B4 · Acceptance criteria

  • One installer file (Fotobox-Setup-x.y.z.exe) installs and launches full-screen on the tablet
  • App auto-starts after tablet reboot
  • Full guest flow (tap → photo → QR → phone download) works on the tablet against the deployed server
  • Offline test: pull Wi-Fi, take photos, restore Wi-Fi, queued uploads flush within 30 s
  • Compositing < 1 s and capture-to-result < 2 s on the tablet

Effort: ~1 day if the tablet is 64-bit Windows 10+; add ~1 day if an Electron downgrade to 22.x is needed (dependency + build-target verification).
